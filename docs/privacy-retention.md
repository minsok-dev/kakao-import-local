# 개인정보 · 보존 정책 (Phase 0/1 필수)

## 1. 수집 경로 표현

개인 카카오톡 대화와 첨부 이미지를 자동 수집하는 **공식 범용 API가 없으므로**,  
PC 다운로드 파일과 대화 내보내기를 사용한다.

## 2. 원본 보존

| 규칙 | 내용 |
|------|------|
| 금지 | 원본 export·이미지 **수정·삭제·이동·덮어쓰기** |
| 허용 | 읽기 전용 스캔, SQLite에 메타·fingerprint·결정만 저장 |
| CLI | delete/원본 변경 명령 **제공하지 않음** |

## 3. 로그

- **전체 메시지 본문**을 애플리케이션 로그에 남기지 않음  
- 로그: 건수, fingerprint 앞 N자, room_key, 오류 코드 중심  
- `LOG_LEVEL`로 제어

## 4. SQLite

| 항목 | 정책 |
|------|------|
| 기본 위치 | `./data/kakao_local.db` (프로젝트 상대, gitignore) |
| 접근 | 해당 PC 사용자 권한; 공유 폴더·클라우드 동기화 경로 비권장 |
| 백업 | 운영자가 수동; 기본 보존 기간은 운영 합의 (문서화 후 설정) |
| 발신자 | 기본은 **저장 가능하되** 마스킹 옵션; 서버 전송 시 최소 필요만 |
| 본문 | 로컬 DB에 matched/merged에 필요한 범위만; 서버에는 **인접 메시지**만 |

## 5. 마스킹

- 전화번호, 개인 링크, 실명(샘플 fixture) 마스킹  
- 서버 전송 payload에 로컬 **절대경로 금지** (상대경로·sha256만)

## 6. 서버 전송 범위

- 필요한 **인접(matched/merged) 메시지**만  
- 채팅방 전체 dump 업로드 금지  
- Import 전용 토큰 사용 시에도 Cookie 저장 금지

### 6.1 대화 export 전체 이력 (운영)

PC 내보내기 txt는 방 **전체 대화**가 올 수 있다.  
로컬 파싱은 전체를 읽되, Import payload에는 인접/merged만 넣는다.

실서비스: **이전 대화 삭제 후 재다운로드·재내보내기**를 권장한다 (운영 합의).  
원본 txt를 도구가 잘라 덮어쓰지 않는다.

### 6.2 원본 TXT 삭제 후에도 남는 로컬 데이터 (보존·purge)

원본 `chats/*.txt`를 운영자가 삭제해도, **이미 파싱된 SQLite 행은 자동 삭제되지 않는다.**

| 남는 것 (예시) | 설명 |
|----------------|------|
| `parsed_message.body_raw` | 파싱된 메시지 원문 |
| `text_merge.before_json` / `merged_text` | 병합 전·후 스냅샷 |
| `text_merge_source` | 출처 메시지 원문·시각 |

**정책 (Phase 3a):**

- 도구가 원본 TXT·이미지·SQLite를 **자동 삭제하지 않음**
- 보존 범위 = 위 로컬 DB + (서버) Import `response_json`의 인접 메시지만
- **수동 purge** (기간·범위·감사)는 향후 백로그 — 별도 CLI/스케줄 설계 후 도입
- 디스크 정리 시 운영자가 DB 파일/`data/` 백업·삭제를 직접 판단

## 7. 인증 (Import)

| 단계 | 방식 | 비고 |
|------|------|------|
| **3a 1차 수동 검증** | 브라우저 **관리자 세션 Cookie** (env로만 주입, 파일 저장 금지) | 스테이징 스모크용 |
| **후속 백로그** | Import 전용 API 토큰 / `actor_type=api_key` | Cookie 방식 대체 |

Cookie·토큰·절대경로·전체 SHA·전체 대화 본문은 **애플리케이션 로그에 남기지 않는다** (prefix·건수만).
